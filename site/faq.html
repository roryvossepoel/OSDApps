Quick answers

A few things worth knowing.

Practical answers for your first deployments.

Why does OSDStage exist?

OSDStage was created to move selected bare-metal preparation before OOBE, particularly with Windows Autopilot device preparation in mind. Device preparation currently has no pre-provisioning mode, so OSDStage can install selected apps, Windows updates and configuration during SetupComplete before user-facing enrollment begins. It complements that flow; it does not replace Microsoft Entra join, MDM enrollment or Autopilot registration.

Where does OSDStage fit with OSDCloud and Autopilot?

OSDStage is designed and tested primarily around OSDCloud, Windows Autopilot and Microsoft Intune. OSDCloud is a natural companion, not a technical requirement: Windows can be applied by another deployment method. OSDStage stages your selected apps, Windows updates and device configuration before first boot; after SetupComplete finishes, normal Windows OOBE, Autopilot or another provisioning flow can continue. OSDStage does not perform Microsoft Entra join, MDM enrollment or Autopilot registration.

Where do I run the Add commands?

Run the Add-OSDStage* commands on the target PC in WinPE, after Windows has been applied and before the first Windows boot. The examples use OSDCloud because that is the workflow OSDStage was designed around. Use a full Windows preparation PC only when you want optional cache preparation or Sync-OSDStage* commands.

When are apps and settings actually applied?

The Add commands stage the deployment in WinPE; they do not install the selected apps there. On the first Windows boot, SetupComplete runs the staged standalone scripts automatically, prepares any required content, installs the queued apps and applies the staged configuration before OOBE continues.

Does OSDStage get installed in Windows?

No. The OSDStage module is only needed in WinPE, after Windows has been applied, while you choose and stage what the device needs. Those choices are written out as a manifest and standalone PowerShell scripts for SetupComplete. On the first Windows boot, those scripts perform the selected work directly; the OSDStage module itself is not used, installed or left behind in the deployed operating system.

Does OSDStage restart the device automatically?

No. Staging and SetupComplete do not force an automatic restart. If an installed component or Windows Update requires a restart, OSDStage records that requirement in the deployment result and delivery report so the normal deployment workflow can handle it.

What do catalog, built-in and repository mean?

The Catalog page shows the components you can use with OSDStage. Built-in app integrations and configuration commands are provided by OSDStage itself. Your repository contains packages that you create and maintain; its catalog.json describes those packages so they can be discovered alongside the built-in components.

Do I need my own repository?

No. You can use all built-in app integrations and configuration commands without a repository. Add your own repository only when you want to deploy packages or scripts that you maintain yourself.

Are built-in apps evergreen?

The built-in app integrations are designed to resolve supported vendor content when acquisition runs during an online deployment, rather than pinning one installer version forever. That makes them evergreen at deployment time; OSDStage does not become the ongoing application-management layer afterward. If the same app is also assigned through Intune or another MDM/application platform, keep that assignment for lifecycle, reset and redeployment scenarios and make sure its detection logic recognizes the version OSDStage installs.

How does the OSDStage cache work?

Caching is automatic when a USB volume labeled OSDCloud is connected. OSDStage detects the volume by label, so its drive letter does not matter, and uses the \OSDStage folder on that volume to store and reuse supported content. A USB cache is optional: OSDStage can also deploy without one and use local staging plus supported online acquisition. For a fully offline deployment, the required matching content must already be available and verified before the first Windows boot.

What if a package fails?

The failure is recorded in the delivery report and local runtime log. Independent packages can still continue, including the final Windows Update pass where its own prerequisites allow it. The failed item remains visible in the overall result, and failed deployments retain their staging information for troubleshooting. OSDStage does not schedule an automatic retry.

Where do I find the delivery report?

After SetupComplete, open %ProgramData%\OSDStage\Results\DeliveryReport.html. The matching DeliveryReport.json sits beside it. Both are generated automatically; no module import or extra reporting command is required. Explore the report and a fictional example.

Why can a successful deployment show Attention?

Attention means the recorded execution can have succeeded while a follow-up action still needs review. Typical examples are a required restart, another Windows Update scan, a skipped result or missing supporting evidence. Read the report summary and checks to see which condition applies.

Does the report work offline?

Yes. The HTML report is self-contained and does not depend on scripts, remote fonts or other internet-hosted assets. You can open it directly on the deployed PC or copy it to another machine for review. Check identifying names and paths before sharing a real report.
